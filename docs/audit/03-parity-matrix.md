# 03. Feature and three-surface parity matrix

One row per capability. **Statuses:** Verified · Partial · Surface-specific · Broken · Absent · Unverified · Not applicable (definitions in the [index](README.md)). **A shared source file is not treated as verification on every surface**: a surface is *Verified* only where a test or observation exercised it there. **Readiness** is the P-level from the rubric ([06](06-production-readiness.md)).

Evidence shorthand: `T:` test file in `test/` · `S:` source path · `R:` runtime observation made during this audit (R1 first-run screenshot, R2 mapper screenshot, R3 History follow-up screenshot, R4 Sheets setup screenshots, R5 no-model screenshot, R6 SQLite probe, R7 axe scan, R8 bisect of browser-test regression; details in [08](08-test-and-verification-report.md)). "Mock model" means a canned response: it proves plumbing, not draft quality. "Stand-in Sheets API" means `test/helpers/sheets-mock.js`: it proves Cold's behaviour against Cold's understanding of the API, not Google's.

**Surface key.** Ext = browser extension (Chrome side panel). Desk = Electron desktop app. Web = the page served by `server.js` (hosted or `npm start`).

## Parity summary

* **Genuinely shared and verified on all three:** the five screens, outreach status, leads (CSV, mapper, edit), copy and handoff links, the data-integrity rules.
* **Intentionally different:** page context and Ask Cold (extension), pairing and SQLite (desktop), server-owned provider (hosted web), on-device model (extension).
* **Presence without three-surface verification:** follow-ups (verified on web only), Google Sheets (verified on web via a fake sign-in; desktop and extension only at the unit/route level), Leads UI on the extension (same module, no Ext-specific test).
* **Absent:** onboarding, reminders, diagnostics, erase-all, CI.
